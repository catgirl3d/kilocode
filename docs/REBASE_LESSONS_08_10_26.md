# Уроки ребейза v7.8.2 → v7.8.7

Разбор ребейза 7–8 октября 2026: где мы потеряли время и что менять в следующий раз.
Обязательные правила перенесены в `FORK_REBASE.md` (разделы Rebase Preflight, Check
Execution Rules, Fold Verification); этот файл — история решений и примеры.

| Старый upstream | `113caf1916` (v7.8.7-2) |

SHA вершин форк-истории здесь намеренно не фиксируются: main форка регулярно
пересобирается (fold, autosquash, чистка хвоста), и любые такие SHA устаревают.
Точки опоры — backup-ветки выше; upstream-коммиты (merge base и старый upstream)
не перезаписываются. Рабочее дерево и индекс на момент финализации были чистыми.

Принятые контракты: модель и effort из архитектуры upstream с
сохранением избранного, on-demand MCP с OAuth-контролами upstream, Welcome без нижнего
блока, retry с сохранением закрытого пустого reasoning, проектная изоляция сессий,
цвета вкладок, локальные теги.

## Что сработало

- Независимая проверка staged-кандидата после каждого стопа поймала реальные ошибки:
  усечённый критерий «грязного» черновика, скатывание API `Default`, ослабленные
  тесты, подмена `mode`.
- Один мутатор в момент времени и переиспользуемые executor-сессии.
- Backup и anchor перед переписыванием истории; сверка дерева после каждого fold;
  split смешанного файла после временного полного коммита.
- Два финальных read-only ревью на замороженном SHA; первая сессия была перезапущена
  с нужными инструментами, а не заменена третьим ревьюером.
- Вопросы пользователю — только на настоящих контрактных развилках (модели, OAuth,
  Welcome, retry/reasoning).

## Уроки

1. **Предварительный, а не исчерпывающий план.** Начать с известных рисков, включая
   автоматически слитый код, и уточнять проверки по реальным стопам. Не нужно до
   первого шага предсказывать все конфликты или получать результаты всех проверок.
   Расширение проверки должно иметь конкретное основание. **Полный CLI suite
   запрещён без прямого требования пользователя.** Координатор и сабагенты не могут
   разрешить его сами через план, baseline, диагностику или расширение проверки.
   Разбивка всех тестов на партии не обходит запрет. Точечные CLI-тесты затронутых
   контрактов разрешены; разрешение на один полный прогон не разрешает повторы.
2. **Baseline по необходимости.** Использовать имеющиеся результаты или запускать
   конкретный тест на старом дереве, когда сравнение помогает установить причину
   падения. Это не обязательный прогон до ребейза. Окружение должно быть сопоставимо;
   старый Bun на новом дереве не заменяет старое дерево. Неустановленное происхождение
   падения нельзя выдавать за доказанный старый дефект.
3. **Локальная проверка не запрещена.** Executor перед передачей кандидата может
   выполнить предусмотренный заданием одиночный тестовый файл или отдельные кейсы,
   lint изменённых файлов и действительно узкую type-диагностику. Команды,
   результаты и ограничения входят в его отчёт. Пакетные и репозиторные suites,
   полные typecheck и сборки запускает только координатор или один назначенный
   валидатор: один тяжёлый процесс за раз. Задание содержит команду или точный scope,
   рабочий каталог и конечный бюджет. Executor не исследует «дешевизну» перед каждым
   разрешённым запуском. Fixture-сервер сам по себе не запрещает одиночный тест;
   незапланированную тяжёлую работу или выход за бюджет передают координатору.
   Обязательная генерация остаётся явно назначенной мутацией одного executor'а и
   занимает тот же тяжёлый слот.
4. **Бюджет без отдельного секундомера.** Использовать прошлые логи или CI, если
   они есть; иначе назначить конечный бюджет по допустимым затратам. Если
   длительность известна, бюджет ставится минимум вдвое больше неё. Длительность
   записывается вместе с нужной проверкой. Повтор неизменённого кандидата только ради
   замера не нужен; проверка старого дерева не заменяет проверку нового. Timeout
   означает незавершённую проверку, а не автоматически зависание или дефект кода.
5. **Проверять инструмент, а не повторять ритуал.** Репетиция surgery нужна перед
   применением неподтверждённой версии или настроек, а не перед каждым ребейзом.
   Для каждой реальной операции сохраняются anchor, однозначность SHA и сверка
   итогового дерева. Ошибка семисимвольного SHA подтверждена для `git-surgeon 0.1.17`,
   не всей ветки версий. Финальные guards выполняются на собранном дереве до ревью.
6. **Decision-batch.** Предсказуемые контрактные развилки решать до старта; фазовые
   границы: после replay уточнить список исправлений, после проверки поведения
   выполнить итоговые guards и финализацию истории, после review новые несвязанные
   дефекты отправлять в follow-up. Смена SHA без изменения проверенных входов сама
   по себе не требует повторных тестов.
7. **Промпты executor'ам**, с контрактами, наблюдаемыми инвариантами
   и точными разрешёнными локальными проверками. Запрет относится к тяжёлым
   агрегатам и несогласованному расширению проверки, а не к любой обратной связи.
   Не обходить типы, не ослаблять тесты, не менять API ради зелёного теста. Зелёный
   локальный тест не заменяет приёмку Bounded/Deep, но координатор не повторяет
   успешную проверку без изменения входов или недостаточных доказательств.
8. **JetBrains-проверки отключены отдельно.** После разбора удалены `typecheck`,
   `test` и `test:ci` из package scripts плагина, а корневой typecheck исключает
   `@kilocode/kilo-jetbrains`. Агентам запрещены Gradle/Java-проверки и установка
   JDK для валидации. Сборочные scripts, wrappers и исходники плагина сохранены для
   явно запрошенной сборки. Это отсутствие проверки, а не успешный тест.

## Ошибки координатора

- Эскалация «проверки затронутых пакетов» до полного CLI-агрегата.
- Watchdog без запаса: лимит 540,0 с при длительности зелёного прогона 542,8 с;
  убитый прогон не доказывает, сколько ему оставалось на самом деле.
- Сжатые промпты без пробелов.
- Перед split не проверил фактический формат SHA в rebase todo.

## Оговорки после ребейза

- Полного baseline старой ветки не было. Для core (конкурентная инициализация
  SQLite), snapshot-ожидания и shell-путей есть сверка исходников с backup и
  повторный запуск на исходном runtime — это сильное, но не полное доказательство;
  IPv6-прогон — скорее нестабильность или влияние соседних тестов, чем доказанный
  старый дефект.
- Окружение между запусками различалось: `SHELL` отсутствовал в одних прогонах и
  указывал на Git Bash в других. Это отдельный дефект воспроизводимости.
