# fork-audit: текущий контракт и исторический постмортем

Этот документ описывает текущий `script/fork-audit.ts`. Текущий контракт сверяется с его
контрактным блоком и реализацией, а правила слоёв и исключений — с `AGENTS.md`. Раздел
«Исторический постмортем» ниже не является описанием текущего вывода или текущего scope.

## 1. Назначение и нецели

`fork-audit` — read-only аудит личного форка относительно Kilo Code. Он проверяет владение
строками форка, покрытие diff-маркерами и корректность размещения обнаруженных маркеров. Это
не общий линтер всех комментариев репозитория и не автоматический редактор исходников.

Цель — отделить изменения форка от исторических изменений Kilo Code и не заставлять ребейз
исправлять чужую разметку. `fork_change` обозначает изменение личного форка, а
`kilocode_change` — слой Kilo Code поверх OpenCode; эти семейства имеют разную severity.

Нецели текущего контракта:

- автоматически добавлять, перемещать или удалять маркеры;
- считать наличие маркера доказательством владения строкой;
- построчно аудировать удаления, rename destinations или бинарные файлы;
- обещать корректный семантический разбор каждого формата конфигурации;
- превращать advisory-отчёты о стиле регионов в fatal gates.

## 2. Четыре слоя маркеров

| Слой | Пути | Правило |
|---|---|---|
| Kilo-exclusive | `packages/kilo-vscode/`, `packages/kilo-ui/` | Только `fork_change`; для нового файла заголовок `fork_change - new file` на первой строке после shebang. `kilocode_change` запрещён. |
| Shared OpenCode | `packages/core/`, `packages/tui/`, `packages/opencode/src/` вне `kilocode/` | Только `kilocode_change`; для нового файла заголовок `kilocode_change - new file`. Для fork-добавления допустим суффикс `[fork]`; `fork_change` запрещён. |
| Kilo backend | `packages/opencode/src/kilocode/`, `packages/kilo-gateway/`, `packages/kilo-memory/` | Допустимы `fork_change` и исторический `kilocode_change`; новый файл может использовать любой из двух заголовков. |
| Исключённые файлы | `test/`, `tests/`, `*.test.ts`, `*.spec.ts`, fixtures, Markdown-документы, JSON/YAML-конфиги, Storybook stories | Маркеры и заголовки не требуются и не должны добавляться. |

В реализации список source-like extensions включает также `.yml`, `.yaml` и `.toml`. Это
список кандидатов для сканирования, а не обещание, что все конфиги парсятся как исходный код:
исключения политики репозитория сохраняются, а семантика YAML literal/folded scalars не входит
в гарантию.

## 3. Сравнение и модель владения

### База сравнения

- Кандидатная база по умолчанию — `upstream/main`; её можно заменить через `--base=<ref>`.
- Фактическая база всегда вычисляется как `git merge-base HEAD <candidate>`.
- В committed mode проверяется диапазон `<merge-base>...HEAD`.
- В `--worktree` рабочие файлы на диске и untracked-файлы сравниваются с вычисленной
  merge-base; staged index отдельно не моделируется.
- `--worktree --base=HEAD` даёт рабочее дерево против `HEAD`, то есть сужает baseline до
  незакоммиченных изменений относительно текущего коммита.

### Владение строками

Источник владения — нормализованный Git diff, а не присутствие маркера.

- Изменение только маркера не создаёт fork-owned строку; маркер на такой строке становится
  redundant.
- Churn сопоставляется по нормализованным строкам: LCS внутри hunk дополняется матчингом
  удалённых и добавленных строк между hunks.
- Одно удалённое вхождение объясняет не более одной добавленной строки. Копии строки, которая
  продолжает существовать в базе, не освобождаются от покрытия.
- В diff нельзя надёжно отличить намеренное перемещение от независимого удаления и повторной
  вставки идентичной строки; консервативный one-to-one fallback трактует такой случай как churn.
- Tooling-директивы, marker-only строки и пустой результат после удаления marker-комментария
  не считаются содержательными fork-owned строками.
- Регион может захватывать неизменённый upstream-контекст, если это минимальная цельная
  конструкция или слияние соседних регионов. Контекст не становится владением форка и может
  появиться в advisory `[CAPTURED]`/`[CONTEXT]`.

## 4. Severity

Fatal означает ненулевой exit status. Для диагностик отсутствие семейства и наличие
`fork_change` считаются fatal; `kilocode_change` без `fork_change` — warning.

| Сигнал | Severity | Действие |
|---|---|---|
| `[MISSING]` | fatal | Покрыть реально добавленные/изменённые строки маркером правильного семейства. |
| `[REDUNDANT]` для fork-маркера | fatal | Удалить маркер, который не покрывает fork-owned или churn-строку. |
| Диагностика `fork_change` | fatal | Исправить placement, структуру или семейство в fork-owned области. |
| Смешанная диагностика (`fork_change` + `kilocode_change`) | fatal | Разделить семейства и устранить ошибочное смешение. |
| Диагностика только `kilocode_change` | warning | Видима в отчёте, но не увеличивает `findings` и не даёт exit 1. |
| Эквивалентная унаследованная structural/nesting-аномалия | подавляется | Не повторяется как новая находка после matching с resolved merge-base. |
| `--inline-report`, `--fragment-report`, `--overwrap-report` и их advisory-сигналы | non-fatal | Использовать для ревью; они не являются gate. |

В частности, текущая реализация не делает `[FRAGMENTED]` или `[INLINE]` fatal. Structural
диагностики `[DETACHED_HEADER]` и `[STRUCTURE_SPLIT]` остаются обычными diagnostics и получают
severity по семейству маркера. Унаследованные эквивалентные structural/nesting-находки не нужно
чинить ради зелёного отчёта.

## 5. Размещение, новые файлы и read-only-поведение

- В JSX children обычный `//` становится видимым текстом; используйте JSX-комментарий
  `{/* ... */}`. Внутри JSX-тега для атрибутов нужен block-комментарий `/* ... */`.
- Маркер нельзя помещать внутрь многострочного комментария или JSDoc. Изменённый JSDoc
  оборачивается регионом снаружи комментария.
- Block-маркер не должен разрывать выражение: операторный хвост после `*/` на той же строке
  считается ошибкой размещения.
- Одиночный trailing-маркер остаётся предпочтительным, когда форматирование стабильно, но
  текущий `[INLINE]` только сообщает о кандидате. Блок вокруг одной строки сам по себе не
  даёт fatal, если нет другой fork-диагностики.
- Tooling-директивы (`prettier-ignore`, `eslint-disable*`, `eslint-enable`) исключены из
  покрытия. Не нужно и нельзя оборачивать их маркерами только ради покрытия.
- Заголовок нового файла проверяется на первой непустой строке после shebang и считается
  whole-file coverage, а не отдельным дублирующим inline-маркером.
- Whole-file заголовок в существующем файле считается ошибкой, кроме неизменённого
  исторического Kilo-заголовка, который уже присутствовал в базе и совпадает с ней.
- `--fix` и `--dry-run`, включая формы с присваиванием, отвергаются. Скрипт не изменяет
  исходники, index, refs или конфигурацию; исправления выполняются вручную.

## 6. CLI и верификация

Текущая форма запуска:

```text
bun run script/fork-audit.ts [--worktree] [--base=<ref>] [--overwrap-report] [--inline-report] [--fragment-report] [paths...]
```

`--help` и `-h` печатают usage. Перед запуском нужно явно выбрать committed или worktree
модель, проверить, что candidate ref доступен, и помнить, что сравнение всё равно идёт с
resolved merge-base. Report-флаги предназначены для ручного разбора, а не для изменения
исходников.

Для Windows нельзя запускать отдельный `sha256sum` на каждый файл из `git ls-files`: такая
проверка замедляется до минут. Используйте агрегированные Git-хэши или один Bun-процесс,
обрабатывающий весь набор файлов.

При работе через агентов scope должен оставаться узким: focused-agent запускает только
регрессионные проверки, относящиеся к своему изменению. Полный suite, typecheck и дорогие
repository guards запускает координатор один раз после всех изменений и deterministic
проверок. Это процесс верификации кода, а не основание расширять scope `fork-audit`.

## 7. Вне контракта

- Удаления, rename destinations и бинарные файлы не получают построчное покрытие.
- YAML literal/folded scalar semantics не гарантируются.
- Скрипт не различает staged index и рабочее дерево; `--worktree` читает диск и untracked-файлы.
- Exempt docs, tests и configs не должны получать marker coverage. Наличие `.yml`, `.yaml` и
  `.toml` в техническом списке extensions не означает, что любой конфиг или его семантика
  проверяются.
- Неподдерживаемые и игнорируемые типы файлов находятся вне аудита.
- Идентичные delete/add и настоящие перемещения неразличимы без дополнительной истории; для
  таких строк действует описанный one-to-one churn fallback.

## 8. Исторический постмортем

Ниже сохранены факты и уроки старого разбора. Указанные commit, пути, количества и примеры
относятся к историческому инциденту, а не являются текущей статистикой `fork-audit`.

### Инцидент массовой переразметки

В историческом commit `662624fff3` (`fix annotation coverage after rebase`) автоматическая
массовая переразметка должна была закрыть coverage, но породила неверное размещение. В старом
отчёте фигурировали примерно 30 переразмеченных файлов. В частности:

- В историческом `TranscriptRow.tsx` `//` внутри JSX children рендерился в интерфейсе как текст.
- Маркеры внутри JSDoc попадали в hover-документацию.
- Маркер посреди выражения выглядел как `disabled={session.mcpLoading() /* fork_change end */ === name}`.
- Блоки закрывались сразу после `prettier-ignore`, а маркеры вставлялись между именами import.
- Trailing-комментарий после `{`, `(`, `=>` или бинарного оператора переносился Prettier на
  другую строку; результатом были исторические пары `MISSING` и `[REDUNDANT]`.

Причина зелёного старого аудита была двойной: он проверял парность, coverage и blame, но не
контекст размещения; кроме того, наличие маркера на upstream-строке само создавало иллюзию
владения. Это был marker-derived ownership hole. Исторический независимый разбор насчитал
59 захваченных строк (27 содержательных и 32 структурных), а также отметил старые примеры
`ports.ts:26`, `KiloProvider.ts:3847-3848`, `instance.ts:2` и `enhance-prompt.ts:1`.

В том же историческом отчёте было два новых файла без заголовка. `opencode-session-headers.ts`
тогда ошибочно пометили как fork, хотя это был файл upstream Kilo Code; для него требовался
исторический `kilocode_change - new file`.

### Что было заменено

- Автоматический writer и read/write-подход, использовавшиеся в старом процессе, retired.
  Текущий аудит read-only и не зависит от доступности writer-а.
- Сравнение с движущимся `upstream/main` и ошибочная модель «worktree по умолчанию против
  HEAD» давали неверный scope при diverged history. Контракт заменён на вычисление
  `merge-base(HEAD, candidate)` и явное различение committed/worktree режимов.
- Старый парсер мог классифицировать `- new file` одновременно как whole-file coverage и
  обычный inline-маркер, создавая ложную двойную диагностику. Отдельно ложными считались
  неизменённые исторические Kilo-заголовки в существующих файлах. Текущий парсер отличает
  header от inline-события и принимает совпадающий исторический Kilo-header из базы.
- Раньше все diagnostics считались fatal, поэтому унаследованные Kilo anomalies блокировали
  работу. Финальный результат семейной политики: fork и mixed — fatal, Kilo-only — visible
  warning, эквивалентные inherited structural/nesting findings — suppressed.
- Историческая Windows-проверка запускала отдельный `sha256sum` для каждого package-файла;
  это превращало проверку в многоминутную операцию. Урок сохранён в текущем правиле об
  агрегированных Git-хэшах или одном Bun-процессе.

Старый overwrap-процесс также пытался шинковать регионы вокруг каждой чужой строки. Это
разрывало функции, imports и JSX; сохранённый урок — выбирать минимальную целую конструкцию,
а `[CAPTURED]` рассматривать как advisory, не как повод менять код. Исторические названия
`[FRAGMENTED_BLOCKS]` и `[INLINE_REQUIRED]` не являются текущими fatal gates.

## 9. Практический checklist при падении аудита

1. Определить режим, candidate и resolved merge-base; не принимать moving `upstream/main` за
   фактическую базу сравнения.
2. Для `[MISSING]` покрыть только реально fork-owned строки и выбрать семейство по слою.
   Не превращать marker-only изменение в новый кодовый diff.
3. Для fatal fork или mixed diagnostics исправить размещение, границы цельной конструкции и
   семейство маркера. Не менять код, не добавлять пустые строки и не дробить выражение ради
   прохождения аудита.
4. Для `[REDUNDANT]` убрать fork-маркер, который не объясняет diff-owned или churn-строку.
   Tooling-директивы не оборачивать.
5. Для Kilo-only warning оставить историческую разметку нетронутой, если нет отдельного
   fork-owned изменения. Эквивалентную inherited structural/nesting-аномалию также не чинить.
6. `--inline-report`, `--fragment-report` и `--overwrap-report` использовать как материалы
   ревью, но не считать их failure.
7. Никогда не редактировать upstream Kilo markers только для подавления warning: это создаёт
   будущий rebase conflict вместо исправления fork-а.
